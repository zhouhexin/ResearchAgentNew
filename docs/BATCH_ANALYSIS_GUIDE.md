# 分批分析论文：失败后接着读，不用全部重来

## 1. 现在怎样读一篇论文

系统会先把 PDF 里的文字拆成片段，然后按顺序分成小批次。

默认每批最多读 **2 个片段**。一批读完后，系统先检查引用是否真的来自这一批原文。检查通过，就把这一批的结果保存下来，再读下一批。

全部批次完成后，再把各批的结果合成一份分析报告。

比如一篇论文有 6 个片段：

| 批次 | 读哪些片段 | 读完后做什么 |
| --- | --- | --- |
| 第 1 批 | 片段 1、2 | 核对原文，保存结果 |
| 第 2 批 | 片段 3、4 | 核对原文，保存结果 |
| 第 3 批 | 片段 5、6 | 核对原文，保存结果 |
| 最后 | 已保存的 3 批结果 | 合成一份报告 |

**合并这一步不再调用模型。** 系统把结论放回“研究问题、方法、贡献、实验、局限”五类中。文字完全相同的结论会合并证据；意思接近但措辞不同的结论可能仍然分别列出，需要你阅读判断。

## 2. 第二批超时，会发生什么

假设第 1 批已经成功，第 2 批超时：

1. 第 1 批的结果已经保存，不会因为第 2 批失败而丢失。
2. 系统默认只给第 2 批再尝试一次。
3. 如果仍然失败，任务会停下来，显示“第 2 批失败”。
4. 你处理好网络或模型服务后，点击“继续未完成批次”。
5. 系统复用第 1 批，只重新处理第 2 批，之后继续第 3 批。

权限、额度或配置错误不适合马上反复请求，系统不会对所有错误都自动重复尝试。修正后仍可继续未完成部分。

只完成几批时，不会发布一份冒充完整结果的报告。**已有的成功报告会保留；新的报告要等本次所有批次完成并通过核验后才会出现。**

## 3. 在页面上怎么用

1. 打开“论文分析”，选择已经导入全文的论文。
2. “阅读范围”默认选择“全文分批分析”。
3. “每批片段数”先保持默认的 2。
4. 点击“开始分析”。页面会显示正在处理第几批、已经保存几批。
5. 全部完成后，查看结果、点击引用核对原文，或下载 JSON。

如果失败，页面会出现“继续未完成批次”。刷新页面后，最近一次未完成任务的进度也会重新加载。

“重新分析”表示从头重新请求各批，旧报告仍保留。它和“继续未完成批次”是两个不同的操作：

| 操作 | 会不会复用已经完成的批次 |
| --- | --- |
| 继续未完成批次 | 会，跳过已经完成并通过核验的部分 |
| 重新分析 | 不会，从头请求模型 |

后端重启会把当时未完成的任务标为中断。已经保存的批次仍在；服务恢复后，手动点击继续即可，不会自动再次调用模型。

## 4. 全文分析和抽样分析有什么区别

- **全文分批分析**：把该份全文的所有片段按顺序放进各批请求中。
- **抽样分批分析**：先从全文中均匀挑选一些片段，再分批分析；可设置“抽样片段上限”。

报告会显示实际提供了多少片段。例如 `109 / 109` 表示全部片段都进入过分析请求；`6 / 109` 表示只提供了 6 个片段。

每个片段进入请求，不代表模型一定会为它输出结论。证据不足的类别仍可为空；你仍需检查结论是否得到原文充分支持。

想先检查模型是否稳定，可以选择“抽样分批分析”，先读 6 个片段，每批 2 个。

## 5. 哪些变化需要重新开始

已保存的批次会和原文、片段编号、模型及分组方式绑定。

下面这些变化会让旧进度不能直接混用：

- PDF 或提取出的正文改变了。
- 重新分片后，原文片段编号或位置变了。
- 换了模型、模型服务地址或结构化输出方式。
- 改了每批片段数、每批字符预算或全文/抽样范围。

页面会提示重新开始。系统不会把不同版本的原文或不同模型的批次偷偷拼成一份报告。

**只增加等待时间或修改额外尝试次数，仍可继续已有进度。**

## 6. 分批后还有没有可能超时

有。分批可以减少每次请求携带的原文，网络不通、模型服务拥堵或额度不足仍可能导致失败。

长论文也会增加请求次数。例如 100 个片段、每批 2 个，大约需要 50 次请求；遇到失败重试时还会增加。因此，全文分析的总时间和费用可能比抽样分析高。

默认设置：

| 设置 | 默认值 | 用普通话解释 |
| --- | --- | --- |
| 每批片段数 | 2 | 一次给模型多少个原文片段 |
| 每批字符预算 | 4000 | 一批原文最多放多少字符；达到限制时提前分成下一批 |
| 每批额外尝试次数 | 1 | 第一次失败后，最多再尝试一次 |
| 每次等待时间 | 400 秒 | 等多久还没得到模型结果，就算这次请求超时 |

不会为了满足字符预算而截断或跳过某个片段。单个片段过长时会提示调整预算或重新分片。

## 7. 如果使用命令行

按顺序分批分析全文：

```bash
python run_paper_analysis.py 23 --batch-size 2
```

这里的 `23` 是论文编号，需要换成自己的编号。

失败后，使用同一条命令继续；系统会检查并复用已经完成的批次。

只抽样 6 个片段来试跑：

```bash
python run_paper_analysis.py 23 --scope sample --max-chunks 6 --batch-size 2
```

明确从头重做：

```bash
python run_paper_analysis.py 23 --batch-size 2 --restart
```

如果用了 `--restart` 后中途失败，继续时去掉 `--restart`，这样才会保留已完成的进度。

旧命令中单独指定 `--max-chunks` 时，仍按抽样模式处理。明确写 `--scope full` 时才覆盖这个默认选择。

## 8. 进度保存在哪里，怎样改设置

批次进度、页面任务和分析结果放在项目的 `outputs/api_tasks.sqlite3` 文件中。不要在分析过程中删除这个文件；删除后就无法继续使用已保存的进度。

论文和原文片段仍然保存在原有 PostgreSQL 中。

可在 `.env` 中设置：

```env
LLM_READ_TIMEOUT=400
ANALYSIS_BATCH_MAX_CHARS=4000
ANALYSIS_BATCH_RETRIES=1
```

修改后重启后端。页面上的“每批片段数”可以直接设置，默认是 2。

分批分析不再用旧的 `ANALYSIS_MAX_CHARS` 限制整篇原文；请使用上面的每批字符预算。分批重试由 `ANALYSIS_BATCH_RETRIES` 统一控制，模型 SDK 不再叠加自动重试，避免一次失败被重复请求很多遍。

## 9. 目前验证到哪里

自动测试已覆盖：第二批超时后保留第一批、只重跑失败批次、读取保存后的进度、原文或模型变化后不混用旧结果、缓存引文再次核验、合并时保留证据，以及命令行续跑。

这些测试使用可控模型回复和隔离数据库。真实模型的速度、网络稳定性和费用仍需在实际使用中观察。
