## 1. 目标与依据

依据 [项目目标](goal.md) 和 [审查建议](ADVICE.md)，下一阶段重点是确认科研结论是否有充分的原文支持，以及如何据此判断研究问题是否得到回答。

当前已经接通计划、检索初筛、人工选文、全文分析、比较、综述、导出和引用查看。现有严格校验能够检查论文和文档归属、原文版本、证据编号及引用是否为原文连续子串，但尚不能据此认定引文在语义上支持结论。

例如，完整复制了“该方法没有超过基线”的原句，也不能使“该方法显著超过基线”成为正确结论。

下一阶段先建立小型人工标注评测集，再实现辅助性的语义证据评审。之后再接研究问题覆盖检查和人工确认的补充研究流程。

## 2. 对 ADVICE.md 的取舍与开发顺序

| 建议 | 处理方式 |
| --- | --- |
| 研究质量评测集 | 首先建立，作为判断评审器实际效果的依据 |
| ClaimVerifier 语义证据评审 | 第一批功能，只给出支持程度判断、依据和待核查提示 |
| 研究覆盖评估与反馈循环 | 紧接语义评审，先评估并推荐任务，再接人工确认执行 |
| 已有文献库直接执行研究计划 | 属于已确认的规划与执行缺口，单独补齐，复用现有有效分析 |
| 统一检索服务 | 先考虑统一现有 arXiv、OpenAlex 和官方核验入口；新增来源继续暂停 |
| CCF 分级 | 后置，属于筛选增强，不能代替论文内容和证据质量判断 |
| PostgreSQL 统一持久化、独立 Worker | 由多用户部署、并发和任务可靠性需求驱动，不作为本阶段前置重构 |
| 文档与基础 CI | 及时修正文档，逐步接现有受控测试；与新增功能分开验收 |

`execution_available=False` 不应简单改为 `True`：需要明确区分“支持分阶段执行”与“支持全自动调度”。当前已经有 `executable_actions` 表达部分能力；已有文献库入口仍须真正接通。

正式发表身份、CCF 等级、检索覆盖范围、结论的语义支持程度是不同信息，不互相替代。

## 3. 本阶段边界

第一版只评审单篇分析里的一个完整 finding：`statement` 加上它引用的全部 evidence 和必要上下文。五个分析类别都适用。

同一结论引用多条证据时，先检查每条证据的真实性，再联合判断是否支持完整结论；不能只取第一条引文，也不能因为某个关键词相同就判为支持。

首版不把一条结论拆成多个新结论。对于含多个主张的结论，必须全部得到支持才能判为 supported；只支持部分内容时，判为 insufficient 并指出未支持的部分。

本阶段保留以下边界：

- 不改变现有 `PaperAnalysis` 结构、原文、证据编号和历史分析，不使已有批次检查点失效。
- 不放宽逐字核验，不让语义模型补写、翻译或改写引文后自动通过核验。
- 不把模型评审当作事实证明，不自动删除原分析结论或修改已发布的历史报告。
- 首版使用单独发起的评审任务，结果供人工核对，不作为所有论文分析的强制发布门槛。
- 不自动二次检索，不自动宣布领域研究空白，不在本阶段新增会议或重构任务调度系统。

## 4. 怎样建立第一批评测样本

### 4.1 选取已有材料

选择三篇优先、两篇也可的已有有效分析论文。尽量兼顾方法介绍和实验结果，并包含至少一个容易误读的结果或局限性段落。

每篇固定一个分析版本、文档版本和对应原文。样本导出只读取保存的分析、引句和上下文，不重新调用模型生成论文分析，也不覆盖原报告。

原文发生改变时，已有评测样本继续保留原快照；补充新版本样本，不能静默替换旧样本的引句和标签。

### 4.2 先少量试标，再扩展至约 30 条

先选 5–8 条，一起确认标签含义、上下文是否足够，以及哪些情况属于歧义。规则稳定后再扩展到约 30 条。

建议构成如下，数量可按实际材料调整：

| 标签 | 建议条数 | 主要考察什么 |
| --- | --- | --- |
| supported | 10 | 正确概括方法、数据集、实验和局限，保留原有条件 |
| contradicted | 8 | 否定关系反转、数值或方向相反、方法主体张冠李戴 |
| insufficient | 8 | 从一项实验推广到所有场景、补造显著性、复合结论只有部分支持 |
| needs_review | 4 | 比较主体或指代不清、上下文存在无法消除的歧义 |

同时覆盖数字、单位、数据集、比较基线、适用条件、中英文概括、多条引文联合支持等情况。

真实分析通常不能自然提供所有错误类型。可以保留真实引句和上下文，仅改动结论，构造受控反例，例如颠倒比较方向或将相对提升改写为绝对百分点提升。

每个受控反例记录 `sample_kind=controlled_negative` 和 `parent_sample_id`；原始分析样本记录 `sample_kind=natural`。反例是评测材料，绝不写回生产分析。

自然样本和受控反例分别统计，不能用人为构造的数据比例估计真实系统的错误发生率。

### 4.3 每条样本保存的信息

建议使用 JSONL 存储完整样本，另导出 CSV 方便人工填写标签；文本里的换行必须由标准 JSON/CSV 库正确处理。

| 字段 | 用途 |
| --- | --- |
| `sample_id`、`dataset_version` | 唯一样本编号和数据集版本 |
| `sample_kind`、`parent_sample_id`、`group_id` | 区分自然样本与反例，并将同源样本放在同一组 |
| `paper_id`、论文标题、`analysis_id` | 确认分析的具体来源 |
| `document_id`、`content_sha256` | 固定全文版本 |
| `category`、`finding_index`、`statement` | 定位被评审的完整结论 |
| `evidence[]` | 全部引用的编号、原始 quote、页码和必要上下文 |
| `reading_scope`、`reading_selection` | 记录全量、抽样或快速阅读及实际覆盖信息 |
| `input_hash` | 标识实际送评的结论、证据和上下文；用于检测材料变化 |
| `annotation_status` | `unreviewed`、`reviewed` 或 `disputed` |
| `gold_label`、`gold_reason` | 人工标签及理由；未标注时为空 |
| `annotator`、标注时间、`annotation_version` | 保留人工标注和修改记录 |
| `split` | 开发集或冻结验证集 |

上下文使用实际原文片段，必要时包含相邻句或相邻片段，记录各自来源。不能用模型生成的解释代替原文上下文。

当前导出的分析快照包含已引用片段的文本和页码，可以作为起点。若还需要相邻片段，应从相同文档版本读取；需要查看表格或图注才能判断时，应人工打开 PDF 核对。

模型评审若没有接收到表格图像等关键材料，不能因为人工看过 PDF 就要求它凭缺失材料作确定判断。应补齐可提供的材料，或明确标为需要人工核对，并记录“模型输入缺失”的原因。

### 4.4 人工标注规则

人工同时阅读结论、全部引句和必要上下文；涉及指标、比较对象和实验条件时，打开对应 PDF 页核对。

| 标签 | 标注标准 |
| --- | --- |
| supported | 材料支持结论的全部主要主张，数值、主体、比较方向和适用范围一致 |
| contradicted | 材料直接否定结论的关键主张，例如基线更优却声称本方法更优 |
| insufficient | 材料与主题有关，但无法支持完整结论；缺少显著性、适用条件或部分主张的依据 |
| needs_review | 在当前可提供材料中存在无法可靠消除的歧义，需要人工进一步核查 |

对于明确、内部无冲突的材料，固定判定次序为：先检查是否有关键主张被直接反驳，再检查是否完整支持；无法完整支持且没有明确矛盾时，区分“缺少依据”和“存在歧义”。在理由中保留混合情况。同一指标的正文与表格若相互冲突，先标记需要复核并记录两处，不按出现顺序自动决定哪一个正确。

标注者之间有分歧时，先将 `annotation_status` 设为 `disputed`，复核后再定标签。不能为了凑够 needs_review 的数量，把所有标注分歧都塞进该类别。未标注和未裁定样本不计入正式评分。

优先两人独立标注后复核；暂时只有一位研究者时，可先形成单人标注版本，间隔后再复核，明确记录其局限。模型可以辅助整理表单，不能替代人工提供标准答案。

### 4.5 开发集与验证集分开

约 30 条样本可参考 18 条开发、12 条冻结验证，但先保证分组隔离，再考虑比例。

优先按论文隔离；材料太少时至少按原始证据和反例家族隔离。由同一结论改出的正例、反例，以及重叠片段，不应分散到两边。共享证据的样本要归为同一组。

开发集用于调整提示词和规则；冻结验证集用于检查调整后的效果。评审模型的输入不包含 `gold_label`、`gold_reason` 或其他暴露答案的标注信息。

若根据验证集的具体错误继续调整提示词，该集合应记录为已经参与开发，另增加未使用的验证样本。反复在同一小集合上调提示词，不能宣称获得独立验证效果。

真实标注数据先保存于 `outputs/evaluations/claim_quality/`，沿用当前 Git 忽略规则；源码中只放经过确认可以共享的最小测试夹具。

## 5. 辅助语义证据评审怎样实现

### 5.1 评审流程

```text
读取固定的分析与原文快照
  → 检查编号、归属、版本和 quote 连续子串
  → 汇集该结论的全部证据与必要上下文
  → 独立发起一次结构化语义评审请求
  → 校验评审输出编号、标签和所引原文
  → 独立保存评审结果及实际送评材料
  → 展示给人工核对
```

“独立”指单独的评审请求和评审指令，不要求额外购买第二个模型服务。可以复用现有 `.env` 下的 API/Codex 配置；同一模型可能重复原分析的错误，必须依靠人工评测识别这一限制。

原文真实性检查未通过时，终止该项语义评审并记录 `precheck_failed`。这属于输入或版本问题，不应伪装成 insufficient 或 needs_review。

输入太长时按结论分批，不截断实际引句，也不无声丢弃关键上下文；超预算项明确记录未评审原因。不要再次把整篇论文重新分析一遍。

### 5.2 结构化输出

建议使用 Pydantic 严格限制以下字段：

- `item_id`：由后端分配，定位固定分析版本中的结论。
- `verdict`：只能为 supported、contradicted、insufficient、needs_review。
- `reason`：简短解释，明确涉及的主体、数值、比较方向或缺失条件。
- `evidence_assessments`：逐条记录引用编号及它支持、反驳或未覆盖的主张。
- `quoted_spans`：如需指出关键原句，只能逐字复制实际送评材料，并保留来源编号。

后端检查返回 item_id 与请求一致、引用均来自本次输入、quoted_spans 确实属于相应原文；不接受模型补造证据编号或改写原句。合法格式和真实引句仍不等于评审判断正确，后者继续对照人工答案评估。

评审模型只分析所给材料，不调用外部检索补全证据，不服从论文正文中夹带的指令，不使用模型记忆中的领域知识替代引用依据。

### 5.3 结果保存与失败处理

评审结果单独关联 `analysis_id`、文档哈希、结论位置和输入哈希，保存模型名称、连接方式、评审规则/提示词版本、运行时间和错误状态，不保存密钥。

缓存键包含输入哈希、分析版本、评审规则/提示词、模型配置和上下文策略；材料或规则改变后不能复用旧结论。模型端点使用不含凭据的标识。

任务运行状态与语义标签分开。超时、连接失败、结构错误应显示为“未完成评审”，而不是 needs_review；重试只处理失败评审项，不重做论文分析。原文或分析变更后，将对应评审标为历史或过期。

前端后续在原结论旁显示“模型评审：支持/矛盾/证据不足/需要人工核对”，同时展示理由、原文引用和版本状态。人工确认或更正另存记录，不覆盖原模型输出。

## 6. 怎么评测与验收

### 6.1 先检查程序，再测真实模型

程序检查使用受控模型响应，覆盖：缺失编号、归属错误、原文改写、多个证据联合判断、非法标签、输入过期、超时、重试和缓存隔离。

其中否定和数字反例用于验证评审流程及标签保存，不把模拟模型给出正确标签当成真实语义判断能力。真正的判断效果必须调用当前真实模型，与冻结人工标签逐项比较。

### 6.2 必须输出的结果

| 指标 | 定义与用途 |
| --- | --- |
| 完成情况 | 总样本数、通过前置核验数、模型成功数、失败数及原因；失败不能无声从报告中消失 |
| 四分类混淆矩阵 | 直接看哪些人工标签被模型误判为哪些标签 |
| 各类准确识别情况、宏平均 F1 | 避免只报告总体准确率；某类无样本或分母为零时标明不可计算 |
| supported 精确率 | 模型判为支持的项目中，人工也判支持的比例，并同时列出分子/分母 |
| 危险误判明细 | 人工判矛盾或不足、模型却判支持的逐例列表；统计其数量和占这两类样本的比例 |
| 弃权与歧义情况 | needs_review 的数量和分布，检查是否只是将所有困难样本都交给人工 |
| 成本与稳定性 | 模型调用次数、耗时、错误数；可获取时记录用量，不编造 Codex token 统计 |

分类指标以有已裁定人工标签且模型成功返回合法结果的样本为分母，并同时报告全体样本的完成率。自然样本与受控反例分别报告；开发集与冻结验证集分别报告。

### 6.3 第一版完成条件

1. 第一批约 30 条样本具有可追溯来源、人工标签、理由和数据版本，或明确列出尚未裁定的项目。
2. 开发集和冻结验证集没有共享证据或反例家族；模型未接触标准答案。
3. 真实模型产生一次可重复检查的评测报告，列出逐例输出、混淆矩阵、危险误判和失败项。
4. 否定、数字和比较方向被误判为 supported 时，逐条分析，修正后使用新的未参与调优样本复测。
5. 原文核验照常工作，评审失败不影响已有有效分析和报告，且可单独恢复。
6. 页面若接入，应能查看判断依据、引句和历史状态，并明确标识模型评审的辅助性质。

不预设没有依据的“90% 即可生产使用”门槛。约 30 条只能帮助发现早期错误、比较规则改进，不能证明跨领域可靠；正式扩大自动化程度前，需要更多不同论文、领域和难例的独立评测。

## 7. 分步开发交付

以下列出分步模块与接口职责；当前 C 已完成，D 已实现待本机真实模型验收，A、E、F 尚未完成。

| 步骤 | 拟交付内容 | 验收产物 |
| --- | --- | --- |
| A | 样本导出与人工标注模板 | 从所选固定分析导出待标注 JSONL/CSV，人工标签默认为空；附校验与分组信息 |
| B | 评测样本整理 | 约 30 条已裁定样本、标注说明、开发/验证划分和数据清单 |
| C | `ClaimVerifier` 与命令行评测 | 严格结构、原文前置核验、逐结论评审、输出验证、逐例结果及统计报告 |
| D | 后台任务与查看入口 | 单独发起、进度保存、失败恢复、结果和原文对照；复用现有任务机制 |
| E | 研究问题覆盖检查 | 根据计划问题、已评审结论和实际阅读范围输出回答情况与缺口 |
| F | 人工确认的补充研究 | 先补读已有材料，必要时补检索；明确预算、最大轮数、停止原因和版本关联 |

通用分析样本导出工具 A 仍待实现；当前已对两份指定 PDF 完成离线样本、全部标注和 C 的真实模型对照。D 已接入独立网页任务，不作为分析或综述的强制发布门槛。两篇标注材料来自 PDF 整理，不能自动视作已有生产分析版本；在页面验收时应选一份当前有效的 PDF 分析。不能把程序实现、受控测试或模型影响后的改标一致率视为语义质量已经达标。

## 8. 后续怎样连接研究覆盖评估

覆盖检查至少区分“尚未检索”“已发现但尚未阅读”“快速阅读未覆盖”“材料支持但比较口径不同”“已读材料仍不足以回答”。

语义评审检查的是结论与所给材料的支持关系；覆盖检查检查的是本轮研究材料能否回答用户的问题。两者不能合并成一个没有依据的评分。

覆盖评估先输出可核对的答案、引用、限制和具体补充任务，供人工确认；即使若干结论被模型判为 supported，也不能因此认定检索充分或已经发现真正的学术空白。
