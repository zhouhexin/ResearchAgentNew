# 项目说明：从一篇论文到一份综述

说明文字更新：2026-10-22。功能状态按现有代码核对，没有因为修改文档而新增功能。

当前单篇分析已改为“少量片段一批、核验后保存、失败继续、最后合并”。页面和命令行共用这套流程，通俗说明见[分批分析使用说明](BATCH_ANALYSIS_GUIDE.md)。

## 1. 这个项目到底帮你做什么

假设你在研究“单光子深度估计”。你通常需要找论文、下载阅读、记下研究方法和实验结果，最后比较不同论文。

ResearchPilot 把这些工作分成几个步骤：

```text
找到论文
   ↓
记进自己的文献库
   ↓
提供论文 PDF，让程序提取文字
   ↓
让模型整理方法、实验和结论，并给出原文出处
   ↓
把多篇论文放在一起比较，写成综述
```

模型输出不是最终事实。程序会检查引用是否来自给定原文，但“这段文字是否真的充分支持这个结论”，仍需要你判断。

## 2. 前端、后端、接口分别是什么

| 名称 | 在本项目里是什么 | 你怎么接触它 |
| --- | --- | --- |
| 前端 | 浏览器里看见的页面、按钮、表格 | 打开 `web/` 启动的网页 |
| 后端业务 | 真正去搜论文、读 PDF、访问数据库、调用模型的 Python 代码 | 目前主要在终端运行 `.py` 文件 |
| 接口（API） | 页面向 Python 提交要求、Python 把结果交回页面的约定和入口 | 例如点击“分析论文”，页面提交论文编号 |
| 数据库 | 长期存放论文资料和原文文字的地方 | 项目使用 PostgreSQL |
| 命令行（CLI） | 在终端输入 `python 文件名.py` 的运行方式 | 例如 `python sync_papers.py` |

目前前端页面和后端业务都已有代码，但连接两者的网页接口还没有实现。
因此，**终端中真实运行的结果，不会自动出现在当前演示页面中。**

## 3. 三张数据库表为什么分开

可以把它们想成“论文登记表、全文材料、原文摘录”。

| 表名 | 存什么 | 举例 |
| --- | --- | --- |
| `papers` | 论文基本资料 | 论文 2 的标题、作者、年份、DOI |
| `paper_documents` | 一份全文的来源和完整文字 | 论文 2 的出版社 PDF，或它的 HTML 全文 |
| `document_chunks` | 从全文拆出来的一小段文字及其位置 | 第 3 页某一段，编号 E21 |

为什么 `papers` 和 `paper_documents` 是“一对多”？
因为同一篇论文可以有出版社 PDF、预印本 PDF、网页全文等多个来源。
每个来源又可以拆出多个片段，所以文档和片段也是“一对多”。

```text
一篇论文 P2
├── 出版社 PDF
│   ├── 片段 E21
│   └── 片段 E22
└── 网页全文
    ├── 片段 E30
    └── 片段 E31
```
设计一对多的原因，是为了兼容这些情况： 
    出版社 PDF 无法获取，先用预印本。 
    预印本与正式版内容不同，需要比较。 
    PDF 和网页提取出的文字各有缺失，需要互相补充。

这些编号只是说明用的例子。当前代码对“同一论文 + 同一来源地址”只保留一条文档记录。
同源内容变化时会更新它，不是为每次变化都保留一份历史。

### 片段和证据有什么关系

论文长，模型一次不一定需要读取全部文字。程序先把原文切成一些小段，这些小段叫“片段”，代码中叫 `Chunk`。

当模型写出某条结论时，它要指出依据了哪个片段，并复制其中的原句。此时这个片段就作为“原文证据”使用。

程序还会保存页码和文字位置，方便找到它来自哪里。PDF 保留实际页码；网页没有 PDF 页码，不能写成“第 1 页”。

### 这几个编号不要混淆

| 写法 | 通俗含义 |
| --- | --- |
| `paper_id=2` / `P2` | 文献库里的第 2 条论文记录 |
| `document_id=3` | 第 3 条全文记录，不是第 3 页 |
| `E21` | 原文片段表中，编号为 21 的记录 |
| `P2:E21` | 引用 E21，并声明它属于论文 2 |
| `chunk_index=0` | 某份文档内部的第一个片段；不等于 E0 |

DOI 是论文的外部识别信息，类似论文在出版系统中的编号；它也不是本项目的 `paper_id`。

## 4. 搜索、导入、分析各做了什么

### 4.1 `sync_papers.py`：先登记论文资料

运行后输入研究主题，程序到 OpenAlex 搜索，然后把标题、作者、摘要、年份等保存到 `papers`。
OpenAlex 可以理解成这个项目使用的论文资料检索来源。

当前一次最多 20 篇，年份范围为 2022—2026。

这一步像把书的目录信息记进清单，**并没有把整本书拿回来**。所以它不下载 PDF、不生成原文片段，也不分析论文。

重复搜索到已保存的论文，会按 DOI 或 OpenAlex ID 检查并复用记录。已有作者、摘要等资料也可能得到补充。
如果一批保存过程中出现身份冲突，当前做法是撤销这一批修改，避免只保存了一半却不清楚哪些成功。
代码里把这种“要么一批成功，要么一起撤销”的做法叫事务。

两个相近脚本的区别：

- `academic_demo.py`：把学术搜索结果写成文件，不加入数据库。
- `main.py`：搜普通网页并读取网页，不负责论文文献库。

### 4.2 `document_demo.py`：把全文放到正确论文下面

```bash
python document_demo.py "data/pdfs/你的论文.pdf" --paper-id 2
```

它会读取 PDF、提取文字、拆成片段，并保存到论文 2 下面。
重复导入相同内容时会复用记录；同一来源内容或片段划分变化时，会更新全文和片段。

新分片使用段落/句子边界滑动窗口：默认每片最多 1200 字符，相邻片段尽量重叠最多 200 字符的完整句子上下文。
窗口只在同一页内移动，文本不改写，页码和字符偏移精确保留。超长句或无标点文本会回退到词/字符边界。
`chunk_overlap=0` 可关闭重叠；自定义 `chunk_size` 时默认重叠上限为 `min(200, chunk_size // 5)`。

你必须确认 PDF 与论文 2 对应。程序不会因为文件名相似，就自动认定是同一篇论文。
如果省略 `--paper-id`，脚本可能按本地文件来源另外建立论文记录，所以给已有论文加全文时应明确填写编号。

想先检查能不能读出文字，但暂不写数据库，可以运行：

```bash
python document_demo.py "data/pdfs/你的论文.pdf" --parse-only
```

PDF 下载目前通常需要先准备好。项目已有“查开放全文地址”和“下载 arXiv PDF”的工具，但还没有接成一键自动下载、解析并保存的完整流程。

### 4.3 `run_paper_analysis.py`：整理单篇论文

```bash
python run_paper_analysis.py 2
```

程序先找到论文 2 的全文，再选取一些片段交给模型，整理成五类：

1. 研究问题：这篇论文要解决什么？
2. 研究方法：它是怎么做的？
3. 主要贡献：作者提出了哪些工作？
4. 实验与结果：怎样验证，得到什么结果？
5. 研究局限：有哪些限制？

每条结论都要带原文引用。没有足够依据的类别可以为空，不强行补内容。

它还会检查：引用编号是否存在、引文是不是原文中的连续文字、分析过程中原文是否发生变化。
仅有换行或空格差异时，可以恢复成原始文字；改了数字、翻译或拼接了句子则不能直接通过。
引用检查失败时，最多请模型修正一次。

**当前默认按批次读取全文；指定 `--scope sample --max-chunks 6` 才是抽样。**
例如显示 `6/28`，意思是文档有 28 个片段，这次只给模型看了 6 个；相邻窗口可能重叠，因此片段比例不是独立文字的阅读比例。
网页及 CLI 分析前会自动迁移可核实的旧版本地 PDF 分片。分片变化会创建新的批次计划，旧版进度保留但不混用。

### 4.4 `run_literature_review.py`：把多篇分析放在一起

它读取 2–5 份不同论文的成功分析文件，检查它们的来源是否仍与数据库一致，先生成比较表，再让模型写综述。

比较的内容包括研究问题、方法、贡献、实验和局限。
综述里用 `P2:E21` 这样的编号，表示“依据论文 2 的片段 E21”。

比较两篇论文的结论，必须实际引用到两篇。传入两个文件但只引用一篇，仍不算完成多论文综述。
输入主题也必须符合论文内容；不能拿激光雷达论文去写医学图像分割综述。

### 4.5 `run_agent.py`：直接向助手提问

助手可以搜索论文资料、在已经导入的本地全文中找片段，再读取片段回答你。

它不会自动下载刚搜到的论文，也不会因为找到摘要就当作读过全文。
当前本地搜索按关键词匹配，不是能够自动理解所有近义表达的语义搜索。

为了避免一直搜索不回答，代码给工具使用设置了最多 5 轮的预算，之后要求模型整理已有结果。

## 5. 文件夹分别用来干什么

| 位置 | 主要职责 | 通俗理解 |
| --- | --- | --- |
| `tools/` | 搜索、网页读取、PDF 下载和文字提取 | 负责取材料的工具箱 |
| `storage/` | 连接数据库、保存论文和原文 | 资料保管和查询 |
| `agent/` | 助手问答、单篇分析、检查引用 | 阅读与分析助手 |
| `review/` | 读取分析、比较论文、生成综述 | 多篇材料的整理工作 |
| `web/` | 页面、按钮、表格、引用侧栏 | 你在浏览器里使用的界面 |
| `data/pdfs/` | 你准备的原始 PDF | 输入材料 |
| `outputs/` | 分析、比较表、综述、错误对照 | 输出结果 |
| `test/` | 自动检查程序行为的代码 | 检查清单 |
| `docs/` | 使用说明和后续开发计划 | 项目手册 |
| `models.py` | 约定论文、文档、片段应有哪些字段 | 资料填写格式 |
| `.env` | 数据库连接和模型密钥 | 私人配置，不提交到代码库 |

想找具体实现时，可按下面的名字查：

| 工作 | 代码位置 |

| 检查综述和数据库是否一致 | `review/db_guard.py` |
| 生成综述、检查跨论文引用 | `review/synthesis.py` |

## 6. 成功结果和错误信息放在哪里

| 文件 | 怎么看 |
| --- | --- |
| `outputs/paper_analysis_论文编号_文档编号.json` | 单篇论文的成功分析；JSON 是按字段保存的文字文件 |
| `outputs/review07/comparison_matrix.csv` | 论文比较表，可用表格软件打开 |
| `outputs/review07/literature_review.json` | 按字段保存的综述结果 |
| `outputs/review07/literature_review.md` | 可阅读、可编辑的综述正文；Markdown 是一种纯文字排版格式 |
| `outputs/paper_analysis_response_error.json` | 模型返回格式不对时的检查材料 |
| `outputs/paper_analysis_evidence_error.json` | 模型引文与原文不匹配时的对照材料 |
| `outputs/review07/review_validation_error.json` | 综述未通过检查时的候选草稿和引用情况 |

综述输出目录可以通过 `--out` 修改。
错误文件是“供排查的材料”，不是通过检查的成功报告。
同名成功文件可能被新结果覆盖，所以当前输出目录不能当成完整的历史记录系统。

## 7. 分析慢或失败时怎样调整

先用一个很小的请求检查模型：

```bash
python run_paper_analysis.py --check-llm
```

怀疑代理问题时，再加 `--no-proxy` 对比。这个选项只影响本次模型连接，不修改系统代理；它也会让客户端忽略环境中的证书设置。

如果小请求正常，但分析很慢，可减少这次阅读的内容：

```bash
python run_paper_analysis.py 2 --max-chunks 4 --max-chars 4800 --timeout 300
```

| 参数 | 意思 |
| --- | --- |
| `--max-chunks 4` | 最多选 4 个完整片段 |
| `--max-chars 4800` | 原文总量不超过 4,800 字符，必要时少选几个片段 |
| `--timeout 300` | 模型读取响应时最多等待 300 秒；不是整个任务总时限 |
| `--retries 0` | 网络失败后不额外自动重试 |

减少片段会减少本次阅读范围，不能把更快的结果理解为已经完整读过论文。
默认等待设置来自 `.env` 的 `LLM_READ_TIMEOUT`；没有配置时是 400 秒。引用修正可能再次调用模型，所以一次分析的总等待可能更长。

## 8. 目前还有哪些没接上

- 浏览器按钮还不能调用这些 Python 程序，需要补网页接口。
- 网页任务进度目前是演示，还没有真正长期保存和执行任务的后台系统。
- 分析和综述主要保存在文件里，还没有完整的历史查询功能。
- 自动获取全文的工具还没有串成一键流程。
- PDF 可以在页面预览，但还不能精准高亮被引用的原句。
- 终端问答、单篇分析、综述的模型设置尚未全部统一。
