# 辅助语义证据评审：命令行对照与网页评审

说明日期：2026-11-13；引用协议更新于 2026-11-16，真实运行验收于 2026-11-17。

当前提供命令行评测和网页辅助评审，只检查固定结论与给定原文的支持关系，不重新分析论文、不修改已有分析。网页默认采用 `references-v2`：模型只选择原文编号，后端直接提取引用文本。命令行默认保留 `verbatim-v1`，用于复现原先冻结的评测；显式选择新协议时另建运行目录，不覆盖旧报告。评审不作为生产分析自动发布门槛。

## 1. 直接运行

在项目根目录、已安装项目依赖的 Python 环境运行：

```bash
python run_claim_evaluation.py
```

默认只选择本地材料包 `outputs/evaluations/claim_quality/two_papers_v1/` 的首批 8 条。人工标注默认读取 `annotation_progress.json` 中当前确认的归档；没有进度文件时回退到 `annotations/pilot_round_001.json`。不会自动运行 Jev-Mem 的 15 条预留验证材料。

HarnessDev 的 15 条开发材料全部完成标注后，显式运行：

```bash
python run_claim_evaluation.py --split development
```

这会核对全部 15 条开发标注，复用先前同配置、同材料的 8 条成功评审，仅请求新增或未完成项目。默认命令仍只处理最初 8 条。切勿将开发集的结果称为独立验证结果。

材料包及人工标注位于 Git 忽略的 `outputs/` 中，不随源码上传。换电脑运行时，需要一并复制本地材料包、`annotation_progress.json` 和 `annotations/`，或用 `--dataset`、`--annotations` 指定对应文件。

默认使用项目 `.env` 中的 API/Codex 连接方式、模型和读取时限。人工标注文件由评分程序读取；模型只收到本条结论、论文标题、全部引句及其原文上下文。构造类型、父样本、人工标签、人工理由和其他样本答案不会进入模型请求。

先只检查材料而不调用模型：

```bash
python run_claim_evaluation.py --check-only
```

成功应显示选定 8 条、人工确认 8 条、模型调用 0 次。这只说明材料和标注能够对应，不代表语义评审通过。

## 2. 两层检查

第一层为确定性的原文检查：

- PDF 文件哈希、页数、逐页提取文本和全文快照一致。
- 所选结论、实际送评材料及人工标注的输入指纹对应。
- 引句为记录页码和字符范围内的连续原文，上下文为该页真实文本。
- 离线证据编号与 PDF 版本和字符位置对应，不冒充数据库 E 编号。
- 输入超预算时拒绝，不截断引句或无声丢弃上下文。

第二层由模型独立评审语义关系：

| 标签 | 含义 |
| --- | --- |
| supported | 全部主要主张及其条件均受材料支持 |
| contradicted | 材料直接反驳结论关键部分 |
| insufficient | 材料不足以支持完整结论或其范围、显著性、因果强度 |
| needs_review | 指代、比较主体不清，或材料存在无法消除的内部冲突 |

每条评审包含总体理由及对全部证据的判断，并引用关键连续原文。后端再次检查返回编号、引用归属及逐字引句；格式正确或引句真实仍不保证模型语义判断正确，需要与人工结果对照。

以下引文恢复规则仅用于旧版 `verbatim-v1` 及其历史请求；新网页评审不要求模型抄写原文，不走这些修复流程。

对模型省略 PDF 换行或改变空格的情况，仅在同一证据上下文中存在唯一的纯空白匹配时，回填实际原文，再执行连续子串检查。模型的标签和理由不改变，返回的原始评审及修复明细另行保存。改词、改数字、标点变化、连字符变化、跨证据拼接和歧义匹配仍不能自动通过。

换行被模型输出为字面量 `\n`、`\r`、`\t` 时，最多撤销两层常见空白转义，仍要求在原证据上下文中唯一匹配，并回填真实连续原文。不执行任意转义解码，不转换 Unicode/十六进制转义。多种解释指向不同位置时拒绝自动修复。

PDF 行尾断词（例如原文 `ar-` 换行 `chitecture`、模型写成 `architecture`）另走候选确认：后端只从同一证据上下文定位唯一的连续原文候选，再单独请求模型选择候选编号。只有全部候选获得明确确认，才回填真实原文并重新执行逐字核验；模型不能返回替换文本，原评审标签和理由不变。普通连字符、文字或数字变化仍拒绝通过。该步骤不修改分类提示词或分类输出结构。

候选确认 v3 在原文和模型引句两侧分别提供行尾断词对照，兼容两边断词位置不同、部分单词已合并而部分仍断行，以及最多两层空白转义叠加的情况。它明确区分单词续接与普通连字符删除，并要求模型返回确认或拒绝的具体理由。对照仅用于辅助确认，不据此自动通过；若返回空列表或理由/结构无效，仍作为运行失败保留。确认请求不包含人工标签，也不更改分类提示词与原评审结论。

连接错误、权限错误、超时、格式错误属于运行失败，不会自动变成 needs_review 或其他语义标签。

## 3. 查看结果

命令末尾打印本次结果路径，默认在材料包的 `review_runs/<配置与输入指纹>/`：

| 文件 | 内容 |
| --- | --- |
| `requests/<样本编号>.json` | 本次尝试调用时准备的独立评审提示词和输入，不含人工答案 |
| `items/<样本编号>.json` | 单条运行状态、尝试次数、模型评审或安全错误信息 |
| `quote_selections/<样本编号>.json` | 行尾断词的原始候选评审、独立确认请求和候选选择结果，不含人工标签 |
| `run.json` | 本次配置、选定编号、保存进度和各项状态 |
| `comparison.json` | 逐项人工与模型对照、混淆矩阵、指标及范围说明 |
| `comparison.md` | 便于直接阅读的对照报告 |
| `comparisons/<人工标注文件哈希>.json/.md` | 人工改标后各轮独立评分记录，保留旧对照 |

这些文件包含本地研究材料，应与原始人工标注分开保管，不把含人工答案的对照报告再发给模型。API 端点仅记录脱敏地址和配置哈希，不记录密钥或驱动异常原文。

## 4. 指标怎样理解

先看选定数量、模型完成数量和人工可对照数量，再看准确率。

分类指标只统计“模型成功返回合法评审，且具有已确认人工标签”的项目，未请求、连接失败、前置核验失败和争议标注不算正确，也不混入语义类别。它们的数量和原因单独保留。

报告给出四分类混淆矩阵、各类精确率/召回率/F1、模型判支持的精确率，以及“人工判矛盾或不足，模型却判支持”的逐例明细。

没有可对照项目时，准确率等指标为不可计算，而不是 0% 或 100%。某类无分母时指标为 `null`。观察到的类别可以计算局部宏平均；四类人工样本不齐时，不报告完整四分类宏平均。

首批 8 条人工标签为支持 6 条、矛盾 1 条、需要复核 1 条，没有证据不足样本。扩展后的 15 条开发标签为支持 7 条、矛盾 6 条、证据不足 1 条、需要复核 1 条。即使开发样本全部一致，也不能称为独立验证或跨领域准确率，尤其后两类各只有 1 条。

## 5. 重试与配置

重新运行同一命令即可继续：成功项目会重新核对材料和已保存评审后复用；失败和未请求项目会再次尝试，不重做论文分析。

对于已保存完整模型候选的引用格式失败，程序先核对同一运行指纹、输入哈希和原始请求，再按受限排版规则尝试恢复；严格核验通过后可直接保存，不重新调用模型。原失败记录写入 `history/<样本编号>/`，保留原模型输出、修复明细及 `recovered_from_diagnostic` 标记。无法验证的候选仍失败，才进入普通重试流程。

若保存的候选仅有可定位的行尾断词，则只请求候选确认，不重新生成分类评审。确认调用遇到网络或权限错误时保留 `pending_candidate_review`，下次继续确认；其他成功项目复用原缓存。未确认的候选不参加评分。

从首批 8 条扩大到 15 条时，程序查找可兼容的已有运行，重新计算其提示词、输出结构、配置及输入指纹，逐条核对原始请求和成功输出。只有全部对应才跨范围复用，并保存 `reused_from_run_key`；不是仅凭样本编号跳过请求。

运行遇到权限、连接、额度或整体服务错误时，停止继续请求其余项目，避免重复失败。已成功部分保留，其余显示 not_attempted。某条评审结构或逐字引文无效时，该条记为失败，仍可处理后续项目。

逐字引文失败时，错误诊断保存未通过核验的候选评审、失败引用编号和候选引句。这些内容不作为成功评审、不参加评分，也不替代人工标签。早期版本的失败记录可能只有错误摘要，不能据此推断具体改写或换行原因。

输入、模型配置、结构化方式、提示词、输出结构或评审规则改变后，使用不同结果目录，避免混用评审。人工重新标注而材料不变时，可复用模型结果重新评分；评分报告按人工标注文件哈希归档，同时更新当前 `comparison.json/.md`。

可选参数示例：

```bash
python run_claim_evaluation.py --timeout 120
python run_claim_evaluation.py --annotations /实际路径/two-papers-annotations.json
python run_claim_evaluation.py --check-only --sample-id CQ-6599e68033
```

显式 `--sample-id` 可指定其他样本，因此不要用预留验证材料反复调提示词。默认首批必须全部具有已确认人工标注，否则在请求前提示，避免悄悄扩大送评范围。

`--split` 与 `--sample-id` 互斥。两个集合均要求所选全部人工标签已经确认；开发与验证使用进度文件中各自的 `split_annotations`，不混用带模型辅助改标记录的开发标签。验证仍须显式启动，不会因开发集完成而自动运行。

Jev-Mem 的 15 条已标注并在模型首次输出前冻结，运行验证：

```bash
python run_claim_evaluation.py --split validation_reserved
```

该命令按 `annotation_progress.json` 的 `split_annotations.validation_reserved` 读取当前标注。初始版本为 `annotations/validation_round_001.json`，初次冻结的标签和评审策略保存在 `gold/validation_v1.manifest.json`。2026-11-16 用户确认 6 条改标后，当前版本已切换为 `annotations/validation_round_002.json`；报告明确标为“留出论文人工复核对照”，指标名称为“复核后的标签一致率”。原始标签及改标前完整验证报告另行保留，模型分类输出不变。

API 单条输出默认 2000 tokens，可配置 `CLAIM_REVIEW_MAX_OUTPUT_TOKENS` 或 `--max-output-tokens`。Codex 输出长度仍由已有 CLI 管理。`--max-input-chars` 默认 24000，超出时不自动压缩材料。`--no-proxy` 仅影响本次调用，不改写 `.env` 或系统设置。

- `evaluation/claim_quality.py`：PDF 来源核验、逐项恢复、独立评分和报告。
- `run_claim_evaluation.py`：读取本机配置并执行首批对照。
- `test/test_claim_verifier.py`：受控逻辑与流程测试。

网页任务和逐结论查看入口现已接通，见下一节；研究问题覆盖评估和自动补检索仍是后续步骤。

## 7. 网页辅助评审

这是对已有生产分析的单独评审任务，与上述人工标注材料包分开保存。评测样本中没有生产 `analysis_id` 的两份 PDF，不会自动变成可在页面评审的分析；先选择文献库中一份已有有效 PDF 分析。

### 发起与查看

1. 启动或重启后端以加载新接口（项目根目录）：`python -m uvicorn api.main:app --host 127.0.0.1 --port 8001`。前端开发代理默认使用此端口；若已配置其他后端地址，沿用该地址。
2. 前端使用真实 API 数据，在“论文分析”选择一份当前有效的已保存分析。论文详情的“AI 分析”页也有相同入口。
3. 点击“辅助语义评审”。程序按结论单独调用 `.env` 中的模型，模型返回判断、理由和原文编号；引用文本由后端直接提取并逐条保存，不重做论文分析。
4. 查看各条“模型评审：支持 / 矛盾 / 证据不足 / 需要人工核对”，阅读理由、逐条证据和连续原文引句。展开“查看送评引文与上下文”可核对完整送评材料。
5. 当前版本的引用可打开现有原文抽屉，并在有本地 PDF 时跳到对应页。抽屉携带送评片段快照；历史版本保留快照文本，不把引用按钮指向已变化的当前原文。
6. 部分失败后点击“继续未完成评审”。同协议的成功项重新核验后复用。旧协议升级时新建独立版本，只导入同分析、同材料和同模型配置下已核验的成功项，并保留旧请求及协议来源；失败和未请求项使用新编号协议重新评审。任务中心可返回对应版本，刷新或切换页面不会取消后台任务。

### 范围与版本

- 首版支持具有真实页码的 PDF 分析，完整保留五类结论，每条联合评审全部证据。一个片段出现多条引句时，使用完整原文片段，避免拼接或漏掉材料。
- 上下文为被引用的完整片段，不补读整篇论文，也不调用外部检索；快读结果的评审仍然只是部分阅读。需要图表或片段外信息时，应另行人工核查。
- 逐字真实性与辅助语义标签分开。运行失败显示“评审未完成”，不转换成任何语义标签。
- 任务与分析版本、原文哈希、实际片段、模型配置、提示词及输出结构绑定。原文或证据变化后旧评审标为历史；模型配置变化后创建新版本，保留原版本。启动时、请求前后和完成前均核对来源。
- 结果在任务 SQLite 中保存版本关系，在 `outputs/claim_reviews/` 保存实际请求、允许编号的输出结构、原文片段目录、模型选择的编号、后端提取结果及失败历史。导入旧成功项时另存 `legacy_import` 来源记录，不冒充新协议重新评审的结果。不会写入生产分析正文或修改已有综述，也不把这 30 条人工答案发给模型。
- 本版提供辅助意见和原文对照，不自动更正原分析、不作发布门槛。人工正式裁定与研究问题覆盖评估属于后续步骤。
- 单条输入字符上限使用 `CLAIM_REVIEW_MAX_INPUT_CHARS`（默认 24000），超过时明确显示未通过前置检查，不截断原文。API 输出预算使用 `CLAIM_REVIEW_MAX_OUTPUT_TOKENS`；Codex 输出仍由现有 CLI 管理。

接口为 `POST/GET /api/v1/analyses/{analysis_id}/claim-reviews` 和 `GET /api/v1/claim-reviews/{review_id}`。请求只接受分析编号，所有结论和来源从服务端固定版本读取。

### 本机验收

先选一份结论较少的现有有效分析，确认评审任务能完成、逐条标签及理由可见、引用能打开原文。刷新后应保留结果；相同配置再次点击应复用。遇到部分失败后继续，应跳过已完成项。不要为测试失败而改动真实数据库，可用受控测试验证来源更新和断线场景。

自动检查覆盖源文身份/哈希/片段/页码变化、调用期间变化、原文与评审引句篡改、模型配置隔离、服务重启恢复、部分失败续跑、输入超预算及页面响应乱序。当前开发环境限制实际 Codex 执行，真实生产分析的页面模型调用与 PDF 浏览器跳转仍以本机验收为准。

### 网页引文断词恢复记录（2026-11-16）

一次真实网页评审共 168 条，已保存 56 条成功结果；4 条因引文断词不同失败，另一次 `CODEX_EXEC_FAILED` 导致其余 107 条未请求。4 条引文涉及“原文和模型都断行但位置不同”“只合并部分断词”及字面量换行转义叠加，例如原文 `augmenta-` 换行 `tion`、模型写成 `augmen-` 换行 `tation`。原有候选定位只处理源文中的断词，未完整覆盖这些情况。

以上为旧版逐字协议的恢复记录。当前网页已升级为下节的原文编号协议：同配置的 56 条成功项经核验后显式导入，旧失败项和未请求项用新协议重新评审，不再继续尝试修补模型抄写的引句。Codex 执行错误仍须与引用问题分开处理。

## 8. 原文编号协议：消除模型抄写造成的引用失配

`references-v2` 的模型响应只有结论判断、中文理由、证据编号及 `span_ids`，没有 `quoted_spans` 字段。后端在请求前将每条证据的完整上下文按整句/段落组合为约 600 字符的片段；长句完整保留，不按长度硬切，不丢弃任何输入字符。目录中的字符范围均相对于对应证据上下文。

本次允许的证据编号和原文编号写入结构化输出的枚举。模型不能通过输出字段提供替代引句。返回后，后端核对样本、全部证据是否齐全、编号是否重复或跨来源，再从固定输入中按字符范围提取实际原文，并执行连续子串核验。任何换行、行尾断词、反斜杠及转义均从原文直接保留，不经模型重新生成，也不需要模糊匹配或事后断词修补。

这消除了“模型重抄引句导致不匹配”这一类故障，不证明语义判断正确，也不保证网络、账号权限和结构化服务始终成功。未知编号、来源变化、超预算或模型调用失败仍明确记为未完成，不能放行伪造引用。

### 现有网页任务怎样继续

重启后端、刷新前端，然后在原分析下点击“继续未完成评审”。程序建立新协议版本，自动核对旧版本的完整输入、模型配置、原请求和成功引文，只导入已核验的成功结果；旧失败项不能据此变为成功。页面显示复用数量与旧版来源，历史选择和页面地址均关联对应版本。原始任务、分类判断、失败记录与原始评测报告保持原样。

当前真实论文的 168 条输入已完成离线检查，396 个原文片段的拼接逐字等于各自完整输入。在临时目录中验证了导入 56 条旧成功结果，生产任务未改写、未发起新模型请求。相关 241 项后端测试通过；新协议真实模型续跑仍以本机操作结果为准。
